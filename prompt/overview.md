리뷰와 별개로, __CR__ 이 무엇을 바꾸는지 설명하는 개요를 작성한다.
이 개요는 __CR__ 페이지의 **첫 코멘트**로 올라간다. 리뷰어가 diff 를 열기 전에 읽는 글이다.

### 무엇을 쓰는가

작성자가 이미 쓴 __CR__ 제목과 설명을 바꿔 말하지 않는다. 그건 리뷰어가 이미 읽었다.
코드를 읽어야만 알 수 있는 것을 쓴다.

- 이 변경의 **중심**이 어디인가. 어느 파일이 실제로 바뀌었고 어느 것이 그에 딸려 왔는가
- 제어 흐름이나 데이터 흐름이 **어떻게 달라졌는가**
- 어떤 **경계**가 움직였는가. 모듈, 계층, 소유권, 프로세스 경계
- 리뷰어가 **어디부터 봐야 하는가**

커밋 메시지를 나열하지 않는다. 변경 파일 목록을 그대로 옮기지 않는다. 둘 다 __CR__ 화면에
이미 있다.

### 어떻게 쓰는가

위의 show-me 문법을 쓴다. 산문으로 길게 풀지 말고, 이 변경에 맞는 표현을 골라 보여준다.
넓은 코멘트 영역이므로 Mermaid 를 써도 된다.

- 흐름이 달라졌으면 Mermaid `flowchart` 나 `sequenceDiagram`
- 호출 경로가 달라졌으면 텍스트 호출 트리, 또는 `diff` 모양의 호출 트리
- 파일 배치나 책임이 달라졌으면 얕은 파일 트리
- 상태 전이나 분기가 달라졌으면 의사코드

분량을 지킨다. 이건 보고서가 아니라 진입점이다. 리뷰어를 diff 로 보내는 것이 목적이지
diff 를 대신 읽어주는 것이 아니다.

- 산문은 코드 블록을 빼고 전부 합쳐 10줄을 넘기지 않는다
- 시각 표현은 하나가 기본이다. 성격이 다른 둘을 꼭 보여야 할 때만 두 개까지 쓴다
- 소제목을 여러 개 세워 문서처럼 만들지 않는다
- 변경이 작으면 두세 문장으로 끝낸다. 오타 수정이나 단일 파일의 국소 변경에는
  다이어그램을 넣지 않는다

### 출력

작업 디렉터리 루트에 `__OVERVIEW_MD__` 를 마크다운으로 쓴다.

- 헤딩을 쓰지 않는다. 게시할 때 Meerkit 이 `## __CR__ 개요` 를 붙이므로, 그 아래에 헤딩을
  또 세우면 위계가 겹친다. 끊어 읽을 곳이 필요하면 문단을 나누거나 굵은 글씨 한 줄로 한다.
- 지적 사항은 여기에 쓰지 않는다. 그건 전부 `__OUTPUT_JSON__` 의 `findings` 로 간다.
- 개요와 리뷰 결과는 둘 다 만든다. 둘 중 하나만 쓰고 끝내지 않는다.
