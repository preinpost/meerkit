이 저장소의 __CR__ 변경분을 코드 리뷰하고, 결과를 JSON 파일로 저장한다.

리뷰 대상 범위: `__DIFF_RANGE__`
`git diff __DIFF_RANGE__` 와 `git log __DIFF_RANGE__` 로 변경분을 파악하고,
필요하면 주변 파일을 읽어 맥락을 확인한다. 리뷰 대상 파일을 수정하지 않는다.

프로젝트 루트에 AGENTS.md, CONTRIBUTING.md 같은 규약 문서가 있으면 그 기준을 따른다.

다음 순서로 본다.
1. 버그와 정합성 — 널 처리, 경계 조건, 트랜잭션 경계, 예외 처리 누락
2. 보안 — 인증/인가 우회, 입력 검증, 민감정보 노출
3. 프로젝트 규약 위반 — 계층 배치, 네이밍, 중복 구현
4. 테스트 — 변경분에 대한 테스트 누락 여부

추측성 지적이나 취향 수준의 스타일 지적은 쓰지 않는다. 근거를 코드에서 확인한 것만 쓴다.

## __CR__ 크기도 본다

한 번에 리뷰할 수 없을 만큼 큰 __CR__ 은 그 자체가 결함이다. 변경 범위가 넓으면 리뷰어가
놓치는 것이 생기고, 문제가 드러났을 때 되돌리기도 어렵다.

리뷰를 시작하기 전에 `git diff --stat __DIFF_RANGE__` 와 `git log --oneline __DIFF_RANGE__` 로
규모를 먼저 재다.

다음 중 하나라도 넘으면 `P1` 로 지적한다.
- 변경 파일 40개 초과
- 커밋 20개 초과
- 변경 라인(추가 + 삭제) 800줄 초과

다음 중 하나라도 넘으면 `P0` 로 지적하고, 나누기 전에는 머지하지 말라고 명시한다.
- 변경 파일 150개 초과
- 커밋 50개 초과
- 변경 라인 3000줄 초과

다만 기계적으로 불어나는 변경은 규모 계산에서 뺀다.
- `pnpm-lock.yaml`, `*.min.js` 같은 자동 생성 파일
- 순수한 파일 이동과 일괄 이름 변경
- 번역 리소스처럼 항목만 늘어나는 파일
- 머지 커밋

이것들을 뺀 뒤에도 기준을 넘으면 지적하되, `suggestion` 에 어떤 단위로 나눌 수 있는지
구체적으로 쓴다. 변경을 실제로 봐야 할 수 있는 말이므로, "나누세요" 같은 말만 쓰지 않는다.

이 지적은 특정 코드 줄에 매이지 않으므로 `file` 과 `line` 을 모두 `null` 로 둔다.

## 사람이 읽는 글이다

각 지적은 __CR__ 의 해당 코드 줄에 코멘트로 달린다. 리뷰어가 훑어보고 바로 판단할 수 있어야 한다.
정확해도 읽히지 않으면 쓸모가 없다.

- `title` 은 40자 이내. 무엇이 문제인지만 말한다.
- `detail` 은 짧은 문단 하나로 시작한다. 첫 문장에 핵심을 두고, 배경은 그 뒤에 붙인다.
- 근거가 둘 이상이면 한 문단에 이어 붙이지 말고 마크다운 목록으로 나눈다.
  줄바꿈은 `\n`, 문단 사이는 `\n\n` 이다.
- 코드 식별자, 파일 경로, 설정 값은 백틱으로 감싼다.
- 물결표를 쓰지 않는다. 범위는 `108-118행`, `수백 ms 에서 수 초` 처럼 쓴다.
- diff 에 이미 보이는 코드를 그대로 옮겨 적지 않는다.
- `suggestion` 은 1-2문장. 무엇을 어떻게 고칠지만 쓴다.

나쁜 예 — 한 문단에 몰아써서 읽히지 않는다:

> `checkRateLimit`(108-118행)은 `countRecent`로 개수를 조회한 뒤
> 통과하면 별도의 락 없이 `sendCode`를 계속 진행하고, 실제 `token` row는 발송이
> 끝난 뒤인 103행에서야 저장된다. 즉 카운트 확인 시점부터 저장 시점까지의 구간이 발송
> 시간만큼 넓게 열려 있어, 같은 키로 짧은 간격의 동시 요청이 오면 여러 요청이 모두...

좋은 예 — 핵심 한 줄, 근거는 목록:

> 재시도 제한이 check-then-act 구조라 동시 요청으로 뚫린다.
>
> - `checkRateLimit` 은 카운트만 확인하고 락을 잡지 않는다
> - `token` row 는 발송이 끝난 103행에서야 저장된다
> - 그 사이 구간이 발송 시간만큼 벌어져 있다
>
> 더블클릭이나 반복 호출이 모두 카운트 0을 읽어 1분당 1회 제한을 그대로 통과한다.

## 출력

리뷰를 마치면 작업 디렉터리 루트에 `__OUTPUT_JSON__` 파일을 아래 스키마로 작성한다.
이 파일을 쓰는 것이 이 작업의 최종 산출물이다. 다른 파일은 만들지 않는다.

```json
{
  "summary": "변경분 전체에 대한 2-3문장 요약",
  "findings": [
    {
      "file": "src/auth.py",
      "line": 156,
      "severity": "P1",
      "title": "한 줄 요약",
      "detail": "핵심 한 문장.\n\n- 근거\n- 근거\n\n영향.",
      "suggestion": "구체적인 수정 방향"
    }
  ]
}
```

필드 규칙:
- `file` 은 저장소 루트 기준 상대 경로. `git diff` 에 나온 경로와 정확히 일치해야 한다.
  __CR__ 전체에 대한 지적처럼 특정 파일에 매이지 않으면 `null` 로 둔다.
- `line` 은 **변경 후 파일 기준 라인 번호**(정수). diff 에서 추가되거나 수정된 라인을 가리켜야 한다.
  해당 지적이 특정 라인에 매이지 않으면 `line` 을 `null` 로 둔다.
- `severity` 는 `P0`, `P1`, `P2` 중 하나다.
  - `P0` — 머지 전에 반드시 고쳐야 한다. 데이터 손상, 보안 구멍, 명백한 버그, 리뷰 불가능한 규모.
  - `P1` — 머지 전에 고치는 것이 옺다. 동작은 하지만 결함이 남거나 프로젝트 규약을 어긴다.
  - `P2` — 고치면 좋다. 개선 제안 수준이며 머지를 막지 않는다.
- 지적할 것이 없으면 `findings` 를 빈 배열로 둔다.
- JSON 외의 설명을 파일에 넣지 않는다.
